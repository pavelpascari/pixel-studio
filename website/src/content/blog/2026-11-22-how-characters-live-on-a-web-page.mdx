Most website pets live in a fixed layer of their own, walking along the bottom of the window and ignoring the
page. `<pixel-stage>` makes the page you already have the level. A card's top edge is
ground, its side a wall, a filled box cover. The characters drop off one card, jump to the next and duck behind a
crate, and the page underneath stays as it was.

The source is
[`packages/runtime/src/pixel-stage.js`](https://github.com/pavelpascari/pixel-studio/blob/main/packages/runtime/src/pixel-stage.js),
documented in the [stage reference](/docs/reference/stage/). Some of it took more than one attempt.

hold to pick it up (or drag it with a mouse), then let go to throw it. The buttons give it orders.

## Opting elements in

Six attributes tell the stage what each element is:


| attribute | the element is |
|---|---|
| `data-pixel-surface` | a platform: characters stand and walk on its top edge |
| `data-pixel-climbable` | a platform whose left and right sides are walls |
| `data-pixel-perch` | a platform they like to sit on, legs over the edge |
| `data-pixel-hide` | a hiding spot to duck behind and peek out from |
| `data-pixel-occluder` | always drawn in front of the characters (a sticky header) |
| `data-pixel-avoid` | never stood on or hidden behind (the main call to action) |

A framework that re-renders a card renders the attribute with it.

## Reading the page rarely

Calling `getBoundingClientRect()` on every card every frame forces layout whenever the page has changed, and would
make the stage the most expensive thing on it. The `World` class keeps a dirty flag instead, set by a handful of
events:

```js
observe() {
  const mark = () => { this.dirty = true; };
  this._ro = new ResizeObserver(mark);
  this._ro.observe(document.documentElement);
  this._mo = new MutationObserver((records) => {
    if (records.some((r) => !this.stage.contains(r.target))) mark();
  });
  // …attributeFilter: the data-pixel-* names and `hidden`
  this._listeners = [['resize', mark], ['load', mark], ['transitionend', mark], ['animationend', mark]];
  for (const [t, fn] of this._listeners) addEventListener(t, fn, true);
  document.fonts?.ready.then(mark);
}
```

Each opted-in element also joins the `ResizeObserver` on its first read. Fonts are on the list because a late web
font reflows every card under it. Mutations inside the stage don't count: the characters change their own attributes
all the time.

Once the flag is set, the next frame reads every box in one batch and rebuilds the platforms. A platform is a
surface's top edge, pulled in off its rounded corners so a character never stands on a curve:

```js
x1: it.l + Math.min(it.radius, (it.r - it.l) / 4),
x2: it.r - Math.min(it.radius, (it.r - it.l) / 4),
y: it.t,
```

<MarginNote kind="field">The stage reads each corner radius once with <code>getComputedStyle</code> and keeps it in a <code>WeakMap</code>. A card whose radius changes later keeps its old insets, in exchange for one <code>getComputedStyle</code> per element, ever, instead of one per read.</MarginNote>

Observers miss movement that leaves layout alone, such as a CSS animation or a transform. The stage re-reads
elements marked `data-pixel-surface="animated"` every frame: a character standing on one rides along by the
platform's `dx`, and one jumping onto it follows it in the air. At a layout read per element per frame, the docs
recommend it for a few elements, not a page full.

## A layer that scrolling does not touch

oneko.js and the other prior art in the [research notes](https://github.com/pavelpascari/pixel-studio/blob/main/docs/research/page-interactions.md)
use `position: fixed` and viewport coordinates, so on a scrolling page every platform moves on every scroll frame.
The compositor does the scrolling, and a character placed from JavaScript trails a frame behind its card.

`<pixel-stage>` is a 0×0 element with `position: absolute; pointer-events: none; overflow: visible`. It places its
characters with `transform: translate()` in document coordinates, so they scroll with the page, already in place. The
passive scroll listener measures speed and nothing else: scrolling reads no boxes and writes no styles.

Each frame runs in three phases: read boxes if the world is dirty, plan and move in plain JavaScript, then write each
character's `transform`, `z-index` and `clip-path` where the string changed. Movement shares the sprites' clock and
capped `dt`, so a slow frame advances body and legs alike and the feet do not slide. Per
[performance.md](/docs/reference/performance/#cost-per-frame), three walking characters add 0.31 ms of main-thread
time per frame in Chrome (1.9% of a 60 Hz frame), and 0.92 ms with the CPU slowed four times.

## Finding the way

The platforms form a graph. From each one, a character can drop off either end onto whatever lies below, jump to a
platform within reach (up to 1.8 times its own height, and three of its widths across), or climb a climbable side
whose foot rests on this platform. Routes come from a Dijkstra search where the cost is pixels walked plus a price for
each action, scaled to the character's height `H`:

```js
const actionCost = { drop: H * 0.8, jump: H * 1.5, climb: H * 2 };
// …
const cost = here.cost + Math.abs(start - here.x) + actionCost[l.kind] + (l.kind === 'climb' ? p.y - l.to.y : 0);
```

Counting hops would send a character on two jumps to save a short walk; with costs, it usually walks to the end of
the card and drops, as you would. Climbing costs the most, plus the height climbed, so a character climbs when no
reasonable jump exists.<MarginNote kind="field">"Usually": the search keeps one arrival point per platform. Sent from the low card to the tall one in the demo above, Moss may first walk to the far end of the low card, because dropping off there reaches the ground cheapest. The search prices the longer walk back along the ground after that choice.</MarginNote>

<MarginNote kind="field">A jump onto a platform that overlaps from above has to take off beside it, never under it, or the character flies up through the card.</MarginNote>

The engine bakes `launch` and `land` events into each jump animation, so the stage knows how long the character is
off the ground. It fixes that flight time and solves for the gravity that fits, which keeps the animation and the
movement in step:

```js
export function jumpArc(x0, y0, x1, y1, lift, flight) {
  const apex = Math.min(y0, y1) - lift;
  const up = Math.sqrt(y0 - apex), down = Math.sqrt(y1 - apex);
  const g = 2 * ((up + down) / flight) ** 2;
  return { vx: (x1 - x0) / flight, vy: -Math.sqrt(2 * g * (y0 - apex)), g, T: flight };
}
```

The crouch plays on the ground; the body leaves at `launch` and touches down at `land`, wherever the target is.
Climbing works the same way: the climb animation carries a `wall` line, where its feet are, and a vertical speed
`speedY`, so the feet stay on the card's edge. Falls run under plain gravity and land on the first platform crossed
from above between one frame and the next, so a fast fall cannot pass through a thin card.

I considered a physics engine and left it out. These characters must not tumble or rotate, and their gait fixes their
speed; a rigid-body simulation would fight both.

## Behind things

`z-index` cannot put a character behind a crate on an arbitrary page. The character would have to join the crate's
stacking context, which a dozen unrelated properties can create, where an `overflow: hidden` ancestor could clip it
and the page's selectors could break. A cut-out in the sprite's own canvas fails too: it is quantised to sprite pixels
and misses the element's edge.

The character stays in the stage layer, above everything, and the stage cuts the hiding spot out of it with
`clip-path: path(evenodd, …)`: the character's box minus every occluder that overlaps it. Under the even-odd rule two
overlapping occluders cancel out and leave a visible patch, so the `cells()` helper first splits the rectangles into
disjoint cells covering their union, rounded to device pixels. Hiding is a duck animation behind the cut, with a peek
over the top every few seconds. The page itself stays untouched.

Occluders are rectangles, and the docs say so: a heading cuts a character with its whole box, not its letters, so
opaque cards, images and filled buttons make the best hiding spots.

## Never in the way

The layer and its characters have `pointer-events: none`, so every click lands on the page as if they were not there.
To let you poke a character anyway, the stage listens in the capture phase on the document and tests each press
against the character's opaque pixels: a hit test in `pixel-sprite.js` copies one sheet pixel into a shared 1×1 canvas
and reads its alpha. A press between a beetle's legs reaches the link behind it, as does a press on a part cut away
behind an occluder.

The page loses one thing: the click that follows a tap on a character, or a throw. The characters take no focus and no
tab stop, and their layer is `aria-hidden`. The accessible control is the pause button, a real `<button>` that
remembers its choice in `localStorage`, as WCAG 2.2.2 asks for motion that starts by itself. Under
`prefers-reduced-motion`, the stage places the characters and they stand still.

## Reacting

A tap shoos a character: it reacts and runs to the farthest place it can reach on screen. Three or more taps, each
within 450 ms of the last, are rage taps: it panics, a little faster with every tap (up to three times its speed), and
the actor fires `pixel-burst`. Movement scales with the playback rate, so even a panic keeps the feet planted.
Scrolling faster than one and a half screen heights a second fires `pixel-fastscroll`, and characters with
`keep-in-view` catch up once the scroll settles.

Scripted moments are data. A scene lists steps (go there, say this, wait for a tap) and can carry a trigger, so the
page arms it without code:

```json
{
  "cast": { "goose": "#goose" },
  "trigger": { "event": "submit", "on": "#signup", "preventDefault": true },
  "steps": [
    { "actor": "goose", "pickUp": "$trigger .letter", "speed": 1.7 },
    { "actor": "goose", "exit": "right", "speed": 1.9 },
    { "emit": "delivered" }
  ]
}
```

A trigger can be any DOM event (`submit`, `click`), a character's own events, or `visible`, half of an element
scrolled into view. The scene skips a step that cannot happen instead of jamming, since the reader may be poking the
characters mid-scene. The "It notices you" section of the [landing page](/) is two of these scenes.

## Every device, and what that costs

Until the latest work, only a mouse or a pen could pick a character up. On a phone, a drag that starts on a character
is a scroll, which the stage must leave to the page, so a finger could only tap.

`touch-action` cannot help: the browser reads it when a gesture begins and ignores later changes. The research notes
weighed a long press that switches the character to `touch-action: none` for the *next* gesture, which means pressing
twice, and shipped tap-only touch instead. Its replacement is a `Gesture` class, kept free of the DOM so tap, hold,
swipe and drag are unit-tested, which makes a finger hold still first:

```js
// A finger that moves before the hold completes is scrolling the page: let it.
if (this.pointerType === 'touch') { if (this.far > GESTURE.holdSlop) { this.mode = 'none'; return 'scroll'; } return null; }
if (this.far > GESTURE.dragSlop) { this._grab(p); return 'grab'; }
```

A press that stays within 10 px for 400 ms picks the character up; a mouse or pen also picks it up once it moves 6 px.
Nothing calls `preventDefault` on a touch's `pointerdown`, and the stage never sets `touch-action`. Once a hold has
completed, a `touchmove` listener cancels the page's scroll, so the finger carries the character. While a finger rests
on a character, the stage sets the page's `user-select` and `-webkit-touch-callout` to `none`, so iOS shows no
magnifier or link callout, then restores the page's own inline values.

iOS starts its own long-press about half a second into a resting touch, after the stage's 400 ms hold, and cancels
the pointer stream, which used to drop a character the moment you picked it up. Touch events for that finger keep
coming, so when iOS cancels the pointer during a hold (or as one is about to complete), the stage carries the gesture
on from `touchmove` and `touchend`: the character follows the finger and flies when it lifts. A `touchcancel` still
drops it.

That `touchmove` listener is non-passive, and a non-passive `touchmove` on the document makes the browser wait for it
before scrolling. [performance.md](/docs/reference/performance/#touch-scrolling) measured the cost on the stage
demo in Chrome, with a Pixel 7 profile and real touch input, 15 swipes per case started away from the characters:

| Case | Swipe to first scroll (median) | 4x CPU |
|---|--:|--:|
| Stage, `grab="on"` (touch listener) | 66 ms | 64 ms |
| Stage, `grab="off"` (no touch listener) | 49 ms | 47 ms |
| Same page without a stage | 32 ms | 31 ms |

That is one frame, with no long frames in the fling that follows. Adding the listener once a hold begins would save
it, and Chrome honours that, but WebKit decides when a touch starts whether its moves can be cancelled, so on an iPhone
the page would scroll away under a held character.<MarginNote kind="field" numbered>WebKit does this by design. The measurement page did not test it there; I have since tried the touch gestures on a real iPhone, with the listener page-wide.</MarginNote>
The listener stays, but exists only while a finger could pick something up: not while paused, not under reduced
motion. Pages that would rather keep that frame can say `grab="mouse"` (the previous behaviour) or `grab="off"`, and
the stage registers no touch listener at all.

The last bug was the smallest and took three tries. After a tap on a character, the stage swallows the click that
follows, so the page does not also follow a link under it. The first version swallowed any click within 500 ms, which
ate quick taps elsewhere. The second swallowed a click at the same spot, until WebKit moved a tap's click onto a nearby
link and it went through. The current rule ties the swallow to the press: the stage swallows that press's click, and
the next press clears it.

## What it does not do yet

Occluders are boxes. The stage treats sticky and fixed elements as if they stayed put, so make them occluders rather
than surfaces; the research notes sketched a second, fixed layer for them, which does not exist yet. Nested scroll
containers and iframes are not supported, and top-layer elements such as modal dialogs always paint above the
characters. The touch gestures have run in Chromium with real touch input, in WebKit with synthesised pointer events,
and on a real iPhone.

The [stage reference](/docs/reference/stage/) has every attribute, event and scene step, and the
[full stage demo](/apps/demo/stage.html) has four characters, a drifting cloud to ride and a scene to play.
